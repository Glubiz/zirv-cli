=== Part 1 of 20: store file, errors and format version ===

Everything lives in the one `--store PATH` JSON file the transactions already live in, side by side under top-level keys: `transactions` (existing), `members`, `expenses`, `transfers`, `history`, and a new `version`. `store.save()` currently rewrites the whole file with only `{"transactions": [...]}`, which would wipe everything else the next time somebody runs `import` or `categorize`. Make saving transactions leave every other top-level key alone (and saving household data must leave the transactions alone too). `import` still replaces the transactions but nothing else.

Error convention for every household command: a user error prints `error: <message>` to stderr, nothing to stdout, exits with status 2, and leaves the store file unchanged. (Messages are given in the parts below.)

Store format version 2:

- The file has a top-level `"version": 2`. EVERY write to the store file by ANY command (including `import` and `categorize`) stamps it.
- `members` is a list of objects `{"name": NAME, "archived": false}`, in the order they were added. `expenses`, `transfers`, `history` and `transactions` keep the shapes described in the other parts.
- A file with no `version` key (or `"version": 1`) is a version 1 file: same layout, except `members` is a list of plain name strings, and transfers or history entries written back then may lack keys that newer ones have. Version 1 files must keep working everywhere: any command that reads one behaves exactly as if it were a version 2 file with every member not archived. They are migrated when something next writes the file (the upgraded file keeps all its expenses, transfers and transactions untouched). A command that only reads must NOT rewrite the file. Change-history entries already in an old file must still undo correctly after the migration.
- A file whose `version` is higher than 2 was written by something newer and must not be touched: every command that opens the store (the old transaction commands included) fails with `error: unsupported store version: N` (N from the file), exit status 2, file left unchanged.

=== Part 2 of 20: members: add and list ===

Put the household logic in a new module `ledgerlite/household.py` and wire a `member` command family into the CLI.

- `python -m ledgerlite member add NAME --store PATH` adds a member and prints `Added member NAME`. Surrounding whitespace in NAME is stripped first. === Part 3 of 20: archiving members ===

`python -m ledgerlite member archive NAME --store PATH` sets the member's `archived` flag and prints `Archived member NAME` (stored spelling). NAME matches case-insensitively. Errors, checked in this order: unknown name (`error: unknown member: NAME`, NAME as typed), already archived (`error: member already archived: NAME`), and a member whose balance isn't exactly zero (`error: member has a non-zero balance: NAME`).

What archiving changes:

- A new expense is only shared between the members who aren't archived: "everyone in the household" means the active members. An archived member can't be an expense's payer (on `expense add` or `expense edit --payer`), can't be named in `--split`, and can't be the sender or receiver of a new transfer: all of those are `error: member is archived: NAME` (stored spelling). For transfers that check comes right after the unknown-member and same-member checks and before the amount checks; for `expense add`/`edit` it comes right after the payer is looked up (and for `--split`, as each name is looked up).
- `balance` leaves archived members out when their balance is zero, but if an archived member does have a non-zero balance (e.g. an old expense they took part in got edited) it still shows them. `settle suggest`, `settle apply` and the reports treat archived members like any other member.
- Old expenses are never touched by archiving: editing an old expense's amount re-splits it between the same people as before, archived or not.

=== Part 4 of 20: renaming members ===

`python -m ledgerlite member rename OLD NEW --store PATH` renames a member and prints `Renamed member OLD to NEW` (OLD in its stored spelling, NEW with surrounding whitespace stripped).

- OLD is matched case-insensitively; unknown is `error: unknown member: NAME`. Renaming to a different capitalisation of the member's own name (`Ana` -> `ANA`) is fine. OLD checks come before NEW checks.
- The new name shows up everywhere the old one was stored: the member entry (archived status unchanged, same position in the list), every expense's payer, weights and shares (keeping their order), and the entries of every transfer. Afterwards every command shows exactly the same numbers as before, just under the new name, and `account OLD` is now an unknown member.
- It is a household change like the others: recorded in the history (label `member rename OLD NEW`, OLD as stored, NEW as stripped) and undoable. History entries that are already there are never rewritten, so they keep showing the old name.

=== Part 5 of 20: expenses ===

`python -m ledgerlite expense add --payer NAME --amount AMOUNT --desc TEXT [--date YYYY-MM-DD] --store PATH`

- PAYER must be an existing member (case-insensitive; the stored spelling is used everywhere), otherwise `error: unknown member: NAME` (as typed).
- AMOUNT is a money amount like `12.34` and must be positive: `error: invalid amount: TEXT` if it can't be read as a number, `error: amount must be positive` if it is zero or negative. (Decimal-place rule: part 9.)
- `--date` defaults to today; a bad date is `error: invalid date: TEXT`.
- Without `--split` the expense is split equally between all active members at the moment it is added (later joiners never get a share of an old expense). Work in whole cents. Each share is rounded down to a cent first, and the leftover cents are handed out one at a time, forward through the participants in participant order, wrapping from the last back to the first. Where it starts depends on the expense's id: for expense number N with P participants it starts at participant number `(N - 1) mod P` counting from 0. So expense 1 starts at the first participant, expense 2 at the second, and so on; with P=3, expense 4 starts at the first again. Expense 1 of 10.00 between Ana, Ben and Cara is Ana 3.34, Ben 3.33, Cara 3.33; expense 2 of the same amount is Ana 3.33, Ben 3.34, Cara 3.33. This rule applies to every expense, equal splits and `--split` ones alike, and to re-splits in `expense edit`. Stored shares of an expense are never recomputed later except by an edit of its amount.
- Expense ids are 1, 2, 3, ... in the order added. It prints `Added expense ID: AMOUNT paid by PAYER` with AMOUNT to exactly two decimals, e.g. `Added expense 1: 30.00 paid by Ana`.

Storage: a top-level `expenses` list, each expense an object with exactly these keys: `id` (int), `date` (`YYYY-MM-DD`), `payer` (stored member name), `amount` (integer cents), `description`, `weights` (object: participant name -> int; for an equal split everyone has weight 1) and `shares` (object: participant name -> integer cents, in participant order, summing to `amount`).

=== Part 6 of 20: weighted splits ===

`expense add` takes `--split NAME=WEIGHT,NAME=WEIGHT,...`:

- Only the listed members take part, in the order they are listed (that is the participant order, not the order members were added). Each share is proportional to the member's weight (`--split Ana=1,Ben=2` gives Ben twice Ana's share). Weights are positive whole numbers; the payer doesn't have to take part. Rounding and leftover cents work exactly as in part 5.
- Names match case-insensitively and are stored in their member spelling; `weights` and `shares` in storage use the participant order.
- Errors: a name that isn't a member is `error: unknown member: NAME`; a malformed or non-positive weight, or anything else that isn't `NAME=WEIGHT` pairs, is `error: invalid split: TEXT` (TEXT the whole `--split` value as typed); the same member twice is `error: duplicate member in split: NAME`.

=== Part 8 of 20: editing an expense ===

=== Part 9 of 20: amounts have at most two decimals ===

=== Part 10 of 20: balance ===

`python -m ledgerlite balance --store PATH` prints one line per member in the order they were added: `NAME: AMOUNT`, where AMOUNT is what the member has paid out for expenses minus the sum of their shares of all expenses, adjusted by settling transfers (part 12), with exactly two decimals. Paid more than their share = positive balance (the household owes them); paid less = negative, with a leading minus, e.g. `Ben: -10.00`. Nothing going on is `0.00`. === Part 11 of 20: settle suggest ===

`python -m ledgerlite settle suggest --store PATH` prints a short list of payments that would bring everybody back to zero, based on the same balances `balance` reports. It must not change the store. Greedy procedure:

1. Among members who owe money (negative balance) take the one who owes the most; among those who are owed money take the one owed the most. Ties in either group go to whoever was added as a member first.
2. The first pays the second the smaller of "what the debtor still owes" and "what the creditor is still owed". Print `PAYER pays RECEIVER AMOUNT` (two decimals), e.g. `Ben pays Ana 10.00`.
3. Reduce both balances by that amount, drop anyone who reaches zero, repeat until nobody is left.

Payments are printed in the order generated, one per line. If nobody owes anything: `Everyone is settled up.` The logic lives in `household.py`, not the CLI handler.

=== Part 12 of 20: transfers ===

`python -m ledgerlite transfer add --from NAME --to NAME --amount AMOUNT [--note TEXT] [--date YYYY-MM-DD] [--settles] --store PATH` records that FROM handed AMOUNT to TO and prints `Added transfer ID: AMOUNT FROM -> TO` (two decimals, stored spellings, e.g. `Added transfer 1: 10.00 Ben -> Ana`). Ids are 1, 2, 3, ... in the order added, separate from expense ids. Note defaults to empty, date to today. Validation, in this order: unknown member (`error: unknown member: NAME`, FROM checked before TO), FROM and TO the same member (`error: cannot transfer to the same member`), archived member (part 3), then amount and date with exactly the same rules and messages as `expense add`.

A transfer is stored as a PAIR of entries written in the same save, never one without the other: a top-level `transfers` list, each item `{"id": int, "date": "YYYY-MM-DD", "note": str, "settles": bool, "entries": [{"member": FROM, "amount": -CENTS}, {"member": TO, "amount": CENTS}]}` (integer cents, debit entry first). `settles` is true only when `--settles` was given. Transfers stored without a `settles` key (older files) count as settling.

Effect on balances: only a settling transfer counts. With `--settles` the sender's balance goes UP by the amount and the receiver's goes DOWN by the same amount. Without it the transfer is just recorded (still stored as its pair of entries, still in `transfer list` and `account`) and has no effect at all on `balance`, `settle suggest`, `settle apply`, or the `Sent`, `Received` and `Net` lines of `report member`.

=== Part 13 of 20: transfer list and account ===

=== Part 16 of 20: settle apply ===

`python -m ledgerlite settle apply [--date YYYY-MM-DD] --store PATH` works out the same payments `settle suggest` would print, in the same order, and records each as a settling transfer: exactly what `transfer add --from PAYER --to RECEIVER --amount AMOUNT --settles` would have stored, with note `settle apply` and the given date (default today; a bad date is `error: invalid date: TEXT` with nothing recorded). Ids continue after the existing transfers. Afterwards everybody's balance is zero, including an archived member who still owes or is owed something (archiving must not stop the payments being recorded). === Part 17 of 20: change history ===

Every command that CHANGES household data appends one entry to a top-level `history` list in the store file, only when it succeeded (a command that fails records nothing). Read-only commands (`balance`, `settle suggest`, reports, `list`/`show`, `account`, `check`...) and the transaction commands (`import`, `categorize`, `list`, `summary`) record nothing. An entry has a sequence number `seq` (1, 2, 3, ..., never reused or reordered), a `label`, and whatever else you need to restore the household data (members, expenses, transfers) to exactly what it was before that change. Labels: `member add NAME` (stored spelling), `member archive NAME` (stored spelling), `member rename OLD NEW`, `expense add ID`, `expense edit ID`, `transfer add ID`, `settle apply`, and `undo #SEQ` (part 18). `python -m ledgerlite history --store PATH` prints one line per entry, oldest first: `SEQ: LABEL`, or `No history.` when empty. Anything that changes household data must be recorded this way.

=== Part 18 of 20: undo ===

`python -m ledgerlite undo --store PATH` undoes the most recent change that hasn't been undone yet: the household data goes back to exactly what it was before that change (so an id the undone change handed out gets handed out again next time) and it prints `Undid #SEQ: LABEL` with the undone entry's seq and label. Calling it again goes one change further back. If there is nothing left to undo it prints `Nothing to undo.` and exits 0. `undo` never touches the transactions that `import` put in the file. The history is append-only: undo must not delete or edit earlier entries; the undo itself is appended as a new entry labelled `undo #SEQ` (SEQ = seq of the entry it undid) and shows up in `history`. Undo entries themselves can't be undone, and an entry that has already been undone is skipped when looking for the next thing to undo.

=== Part 19 of 20: check ===

`python -m ledgerlite check --store PATH` is a sanity check that only READS: it never rewrites the file (not even to migrate an old version) and doesn't touch the history. It prints one line per problem: all expenses first, in stored order, then all transfers in stored order.

For each expense, in this order:

- `expense ID: shares total X.XX but amount is Y.YY` when the integer-cent shares don't add up to the amount (two decimals each);
- `expense ID: unknown member NAME` for every name that isn't a member (archived members are members): payer first, then the `weights` names, then the `shares` names, each distinct unknown name reported once, in order of first appearance. Names compare exactly, capitalisation included.

For each transfer, in this order:

- `transfer ID: entries do not balance` when it doesn't have exactly two entries, or their amounts don't add up to zero;
- `transfer ID: unknown member NAME`, same rules, over the entries' members in order.

No problems: prints `ok` and exits 0. Problems: prints them and exits 1. A store that doesn't exist yet, or is empty, is `ok`. It works on version 1 files too, without rewriting them. Nothing the other commands do should ever produce a problem here.
