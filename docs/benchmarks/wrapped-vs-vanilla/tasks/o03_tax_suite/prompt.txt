=== Part 2 of 20: my own categorisation rules ===

Add a module `ledgerlite/rulebook.py` for user rules, stored under a top-level `"rules"` key as a list of objects with `id`, `pattern`, `category` and `priority`.

- `python -m ledgerlite rules add --pattern P --category C [--priority N] --store PATH` adds a rule (priority an int, default 0) and prints `Added rule ID: P -> C (priority N)`. Ids are 1, 2, 3... (one more than the highest existing id). An empty or whitespace-only pattern is `error: pattern must not be empty`.
- `python -m ledgerlite rules list --store PATH` prints one line per rule in id order, `ID: P -> C (priority N)`, or `No rules.` when there are none (also when the store file doesn't exist yet).

Matching: a rule matches a transaction when its pattern appears, case-insensitively, anywhere in the payee or the memo. When several of my rules match one transaction, the winner is the one with the highest priority; if priorities tie, the MOST RECENTLY added rule wins (the highest id), regardless of how long the patterns are. My rules always beat the built-in `DEFAULT_RULES`, whatever their priorities; the built-ins are only consulted when no user rule matches.

This applies everywhere rules get applied: `categorize` (same `Re-categorized X of Y transactions` output as today), `import` (still only touching rows that arrive without a category; read the user rules from the `--store` file before it gets overwritten, if the file exists) and `merge` (part 7).

=== Part 4 of 20: clean merchant names ===

My statements are full of noise (`WHOLE FOODS MARKET #221`, `LYFT RIDE 001`, `ALDI 2044`). Add `ledgerlite/merchants.py` with `normalize_payee(raw: str) -> str`. The canonical form:

1. collapse any run of whitespace to a single space and trim the ends;
2. drop every token that is `#` followed only by digits (`#221`);
3. then, if more than one token is left and the LAST token is made only of digits and is at least 3 digits long, drop it too (`LYFT RIDE 001` -> `LYFT RIDE`, but `SHELL 12` stays and so does `T-1234`);
4. keep the original letter case;
5. if that leaves nothing at all (e.g. the payee was just `#55`), return the whitespace-collapsed input unchanged.

`import` normalises every row's payee. When normalisation actually changes the payee, `payee` holds the clean name and `raw_payee` holds the original statement text; when it doesn't change, `raw_payee` stays `""`. Normalise BEFORE categorising, so categorisation sees the clean payee.

=== Part 6 of 20: merge a statement without duplicates ===

`python -m ledgerlite merge CSV_PATH --store PATH [--window DAYS]` reads the CSV exactly like `import` does (same payee normalisation, same categorisation with my rules and the built-ins), but instead of replacing the ledger it ADDS the new rows to the transactions already in `--store` (a missing file starts a fresh ledger). New rows get ids continuing after the highest id already in the store (an empty or new store starts at 1), in CSV order.

An incoming row is a DUPLICATE, and is skipped, when the ledger already holds a transaction with the same payee after normalisation (compared case-insensitively, normalising the stored transaction's payee too, since old rows may still carry noisy statement text), exactly the same signed amount (a refund of the same size is NOT a duplicate of the charge), and a date within `--window` days of the incoming row's date, either side, inclusive. The window defaults to 2 days; `--window 0` means same date only. A negative window is `error: window must be >= 0`, touching nothing.

Print `Merged A new transactions, skipped D duplicates` (always that wording, even for 1): A rows added, D skipped. Everything else in the store (rules etc.) stays untouched. Put the duplicate check in its own module `ledgerlite/dedupe.py`, and share whatever import and merge have in common instead of copying it.

=== Part 7 of 20: merge matches one-to-one ===

An existing transaction may cancel out only ONE incoming row. Go through the incoming rows in file order; each is matched against the existing (already-in-the-ledger) transactions that fit the duplicate rules of part 6 and that have NOT already been matched by an earlier row of this same file. If several unmatched existing transactions fit, take the one whose date is closest to the incoming row's date, and if two are equally close, the one with the lower id. A matched row is skipped as a duplicate; a row with no unmatched partner left is added as new. Rows from the same file never match each other (two identical rows are both new if the ledger has nothing like them); only transactions that were in the ledger before this merge can absorb a row. So one coffee in the ledger plus two identical ones in the file means one duplicate skipped and one new coffee added, and merging the exact same file a second time adds nothing. Output wording is as in part 6.

=== Part 8 of 20: split a transaction across categories ===

Add `ledgerlite/splits.py` and two commands.

`python -m ledgerlite split ID --part CATEGORY=PERCENT [--part ...] --store PATH` splits transaction ID. Percentages may be decimals (`33.33`) and must add up to exactly 100; at least two `--part` options are required. Parts are kept in the order given. On success print `Split transaction ID into N parts`. Errors (stderr, exit 2, store untouched): `need at least two --part options`, `percentages must sum to 100`, `bad --part 'TEXT' (expected CATEGORY=PERCENT)` (for a malformed or non-positive part), and `no transaction with id N`. Splitting an already-split transaction replaces its old split.

`python -m ledgerlite split-show ID --store PATH` prints one line per part, `CATEGORY: AMOUNT` (2 decimal places, with the transaction's sign), in the stored order. For a transaction that isn't split it prints `Transaction ID is not split` (exit 0). Unknown id is the same `no transaction with id N` error.

The money: each part's amount is a whole number of cents and the parts add up to the transaction's amount EXACTLY. Each part gets floor(|amount| in cents x percent / 100) cents; the leftover cents (fewer than there are parts) are handed out one cent each to the FIRST parts, in the order given. All parts carry the transaction's sign. Example: -100.01 split 50/50 is -50.01 and -50.00; -10.01 split 33.33/33.33/33.34 is -3.34, -3.34, -3.33.

Storage: a split transaction gets a `"splits"` list of objects `{"category": ..., "percent": ..., "amount": ...}` in part order, all three values strings (`percent` exactly as typed, `amount` like `"-50.01"`); unsplit transactions have an empty list. The transaction's own `category` and `amount` stay exactly as they were.

=== Part 15 of 20: search ===

`python -m ledgerlite search QUERY --store PATH`, where QUERY is ONE string made of terms separated by whitespace; shell-style quotes work inside it, so `payee:"whole foods"` is a single term. A transaction is a hit only if it satisfies EVERY term. Terms:

- `payee:TEXT`: TEXT appears (case-insensitive) in the transaction's payee as a clean merchant name, i.e. the same cleaned-up form the duplicate detection compares, not the raw statement noise;
- `category:NAME`: the category equals NAME (case-insensitive, whole name, not a substring); for a split transaction a match on ANY of its parts' categories counts too;
- `year:YYYY`: dated in that calendar year;
- `tax:yes` / `tax:no`: the tax-deductible flag;
- `amount>N`, `amount<N`, `amount>=N`, `amount<=N`: compare the ABSOLUTE value of the amount (so `amount>40` finds a -45.67 expense and a 2500.00 paycheque alike);
- a bare word (no colon): the word appears case-insensitively in the payee or the memo.

Print one line per hit in the same row format `tax list` uses (id, date, amount, payee), ordered by date and then id, followed by a final line `N matches` (always that wording, even for 1; `0 matches` for none; an empty query matches everything). A term with an unknown field (`colour:red`) is `error: unknown search term 'colour:red'`; a bad value (`tax:maybe`, `year:abc`, `amount>lots`) is `error: bad value in search term 'TERM'`; both go to stderr with exit 2 and nothing on stdout. Search never modifies the store. Put the parser in a new `ledgerlite/query.py`.

=== Part 16 of 20: backup ===

Logic in a new `ledgerlite/backup.py`. `python -m ledgerlite backup --store PATH --out FILE` copies the store file to FILE byte for byte (everything in the store, all top-level keys, not just transactions), and next to it writes a checksum file named FILE plus `.sha256` (e.g. `backup.json.sha256`) holding the lowercase SHA-256 hex digest of FILE's bytes followed by a newline. Print `Backed up N transactions to FILE`, N = the number of transactions in the store. If the store file doesn't exist: `error: no such file: PATH`, exit 2, nothing written.

=== Part 17 of 20: restore ===

`python -m ledgerlite restore FILE --store PATH` replaces the store with the backup, but only after the integrity check: FILE's own SHA-256 must equal the digest in the checksum file (compare ignoring case and surrounding whitespace). It prints `Restored N transactions into PATH`. If FILE doesn't exist: `error: no such file: FILE`. If the checksum file is missing: `error: missing checksum file FILE.sha256` (with the real path). If the digest doesn't match: `error: backup integrity check failed`. Every error exits 2 and leaves the current store completely untouched (the integrity check happens BEFORE anything is written). The store file is created if it didn't exist.
