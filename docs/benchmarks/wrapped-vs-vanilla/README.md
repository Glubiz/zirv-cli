# wrapped-vs-vanilla benchmark harness

This is the benchmark harness used to produce the wrapped-vs-vanilla numbers
referenced by `docs/benchmarks/wrapped-vs-vanilla.md` and the README. It is
copied here verbatim (minus run output) so the numbers are reproducible from
this repository. See `CONTRACT.md` for the full spec.

## What it measures

Each task in `tasks/` (t01-t12 small, t13-t15 large, t16-t21 XL -- see
"Large-task grid" below) is run against a fresh copy of the `template/`
("ledgerlite") repo under one of these conditions:

- `vanilla` -- `claude -p` directly, prompt on stdin. With
  `--vanilla-plugin-dir` (used for the current grid) it instead loads a
  plugin such as obra/superpowers, drops the user settings layer (so the
  operator's own global zirv hooks can't leak in) and restates
  `bypassPermissions` explicitly, so the plugin's own `SessionStart` hook
  still runs.
- `zirv` -- `zirv ctx exec --agent claude --prompt <prompt> -- ...`.
- `zirv-proxy` -- `zirv ctx proxy --json <prompt>` first (to pick a seat
  tier / model and optionally start a workflow), then launches like `zirv`
  with a `[zirv proxy]` layer prepended to the prompt.
- `zirv-jev-full` (issue #758) -- identical launch to `zirv-proxy`, with
  every `[jev]` advisory gate (`config.rs::JevConfig`: `memory`,
  `supervisor`, `dispatch`, `review`, `gates`, `context`,
  `intake_savings`, `review_reuse`, `harvest_screen`, `admin_dispatch`)
  turned on via `ZIRV_CTX_JEV_*` env vars for the proxy call, the
  workflow start, and the exec launch alike -- isolates every advisory
  site's effect beyond zirv-proxy's own intake routing. Needs a Jev
  credential in the environment, same as `zirv-proxy`.
- `zirv-jev-<gate>` (issue #758) -- same as `zirv-jev-full` but with only
  that one gate on, e.g. `zirv-jev-memory`, `zirv-jev-dispatch`. Cheap
  per-gate ablations for deciding which gates earn default-on status.

Plugin and hook parity (2026-09-24, d256124e):
- **zirv conditions keep the user settings layer.** zirv's own hooks (Stop, UserPromptSubmit, PreCompact, PreToolUse) are installed in `~/.claude/settings.json`, so a zirv launch with `--setting-sources project,local` silently runs without them. Rounds r1–r3 in `results/2026-09-24-fix-loop/` did exactly that.
- **Vanilla gets the same plugins through `--settings`.** Its `--setting-sources project,local` branch (used with `--vanilla-plugin-dir`) receives the operator's `enabledPlugins` from `~/.claude/settings.json` that way, so both sides load the same unrelated operator plugins and only zirv's hooks differ.

`--noninteractive` prefixes every condition's prompt with the same
"nobody will answer questions" notice, so a plugin that likes to stop and
ask (superpowers) can't win on wall-clock/cost by stalling instead of
finishing. `--zirv-dir <dir>` prepends a specific `zirv.exe` build to PATH
(used to test a not-yet-released build against the installed one).

Each run is graded (tests, answer-check, or judge rubric, per task) and
scored, timed, and cost-tracked; `aggregate.py` rolls the per-run
`result.json` files into a report.

## Reproducing the recorded grids

From this directory, current grid (zirv under test vs. vanilla + superpowers,
2026-09-23):

```
python run.py --tasks all --conds vanilla,zirv,zirv-proxy --reps 3 --model sonnet --parallel 3 \
  --noninteractive --vanilla-plugin-dir <path to obra/superpowers plugin> --zirv-dir <path to zirv.exe under test>
python aggregate.py --runs runs --out report-opt-sonnet.md

python run.py --tasks all --conds vanilla,zirv --reps 2 --model haiku --runs-subdir runs-haiku --parallel 3 \
  --noninteractive --vanilla-plugin-dir <path to obra/superpowers plugin> --zirv-dir <path to zirv.exe under test>
python aggregate.py --runs runs-haiku --out report-opt-haiku.md
```

Earlier grids used fewer tasks and different vanilla conditions -- pass
`--tasks t01,t02,...,t12` to hold the task set at twelve, drop
`--vanilla-plugin-dir`/`--noninteractive` to reproduce the original
disableAllHooks vanilla, or keep
`--vanilla-plugin-dir` without `--noninteractive` to reproduce the
superpowers-baseline grid where vanilla could still stop to ask. See
`../wrapped-vs-vanilla.md` for what each grid means and why they aren't
directly comparable.

`run.py` is stdlib-only (Python 3.11+) and self-bootstraps: it locates
`claude`, `git`, `zirv`, and (on Windows) `taskkill` via `PATH`, falling back
to the hardcoded paths used on the machine the harness was developed on if
`which` can't find them. `template/` must already be a pristine git repo
(one root commit, clean tree) before a run starts -- `run.py` refuses to
copy from a dirty template rather than silently committing over it.

`runs*/` output directories (created by `run.py`) are git-ignored -- they are
regenerated by the commands above, not checked in.

Issue #788's operator-only, off-by-default `[headless]` cost levers
(prompt-cache TTL, per-complexity effort, lean/`--disallowedTools`) apply to
every `zirv`/`zirv-proxy` condition automatically -- `run.py` needs no flag or
env for them, since `zirv ctx exec` reads the SAME operator config
(`~/.zirv/ctx.toml`) the harness under test already uses. To measure them,
set the table in that file (or export the matching `ZIRV_CTX_HEADLESS_*`
vars, e.g. `ZIRV_CTX_HEADLESS_PROMPT_CACHE_TTL=1h`) before running the grid,
same as any other operator config change; `result.json`'s
`cache_creation_ephemeral_1h_input_tokens`/`_5m_input_tokens` (from the `-p`
JSON result's `usage.cache_creation`) show whether the configured TTL
actually shifted cache-write billing. See the top-level `README.md`'s own
"Headless cost levers" section for the full `[headless]` reference.

## Large-task grid (t16-t21 XL, t22 EPIC)

t13-t15 ("LARGE") turned out to still be small for a wrapper built for
long-running work -- vanilla Sonnet finished even the largest of them in
under a minute for well under $0.20. `t16_tags`, `t17_schema_migration`,
`t18_ledger_layer`, `t19_goals_saga`, `t20_audit_log`, and `t21_search`
("XL") are sized for roughly 10-30 minutes each (t19_goals_saga, a
7-phase saga, is meant to be the longest of the XL tasks, at 30+ minutes),
each spanning several files. `t22_envelopes` ("EPIC") is bigger still: 10
ordered phases building an envelope-budgeting subsystem across 6
new/touched modules, a 512-line reference diff, and 41 hidden cases --
sized for 30-60+ minutes. All seven are `kind=tests`, each with a
`reference.patch` solution proven end to end (pristine template scores 0,
the reference solution scores 1.0 with `visible_ok: true`) -- see
`tasks/README.md` for the per-task grid and shapes. Reproduce the combined
large-task grid (t13-t15 + t16-t21 + t22) with `--timeout-min 60` (raised
from 45 to give t22 enough room):

```
python run.py --tasks t13_recurring,t14_bugsweep,t15_reports,t16_tags,t17_schema_migration,t18_ledger_layer,t19_goals_saga,t20_audit_log,t21_search,t22_envelopes \
  --conds vanilla,zirv,zirv-proxy --reps 3 --model sonnet --parallel 2 --stagger-s 90 --timeout-min 60 \
  --runs-subdir runs-large \
  --noninteractive --vanilla-plugin-dir <path to obra/superpowers plugin> --zirv-dir <path to zirv.exe under test>
python aggregate.py --runs runs-large --out report-large-sonnet.md
```

`reference.patch` files live under `tasks/<id>/` for reference only; like
every other task file besides `template/`, they are never copied into an
agent's own working copy (`run.py` copies only `template/` into
`<run>/repo`, and each grader's `hidden/*.py` copy is the only other thing
that crosses into a run's repo).

python run.py --tasks all --conds vanilla,zirv,zirv-proxy,zirv-jev-full --reps 3 --model sonnet --parallel 3 \
  --noninteractive --vanilla-plugin-dir <path to obra/superpowers plugin> --zirv-dir <path to zirv.exe under test>
python aggregate.py --runs runs --out report-jev-full-sonnet.md

Or list individual `zirv-jev-<gate>` conditions (any subset of `memory`,
`supervisor`, `dispatch`, `review`, `gates`, `context`, `intake_savings`,
`review_reuse`, `harvest_screen`, `admin_dispatch`) alongside `zirv-proxy`
for a cheaper per-gate ablation:

```
python run.py --tasks all --conds vanilla,zirv-proxy,zirv-jev-memory,zirv-jev-dispatch \
  --reps 3 --model sonnet --parallel 3 \
  --noninteractive --vanilla-plugin-dir <path to obra/superpowers plugin> --zirv-dir <path to zirv.exe under test>

```

`--dry-run` prints each condition's argv plus the `ZIRV_CTX_JEV_*` env
additions it would set, without calling the proxy or spending anything --
use it to sanity-check a `--conds` list before running the real grid.
`aggregate.py`'s report pairs every `zirv-jev-*` condition against both
`vanilla` and `zirv-proxy` in its "Robustness" section, and its
"zirv-proxy decisions per task" table is grouped by (task, condition) so
mixed conditions in one report don't blend together.

## Long-session chain

Every task above is a single prompt that finishes in 1-3 minutes -- it never
exercises what zirv is actually for (scoring context rot across a LONG
session, compacting or handing off before a session degrades, carrying
memory forward). `kind=chain` tasks close that gap: `tasks/<id>/prompts/
01.txt .. NN.txt` are sent one after another to the SAME agent session, like
a developer working with it for an afternoon, with the context growing large
enough across the whole chain that session management matters. `t23_afternoon`
is the current one (9 steps on the `ledgerlite` template: features that
build on each other, a bug report on something the agent itself built two
steps earlier, a mid-chain refactor, a request referencing an earlier
decision, a change of mind that partially reverts a step, and a final
README-plus-summary wrap-up).

```
python run.py --tasks t23_afternoon --conds vanilla,zirv-nojev,zirv-jev-full --reps 2 --model sonnet \
  --parallel 2 --timeout-min 120 --noninteractive \
  --vanilla-plugin-dir <path to obra/superpowers plugin> --zirv-dir <path to zirv.exe under test>
python compare.py --runs runs --baseline vanilla
```

`--timeout-min` is a budget for the WHOLE chain, not per step. `compare.py`
needs no flag to notice a chain run: any `result.json` with a non-empty
`"steps"` list gets an extra "Long-session chain (per step)" table (step ->
score/cost/min per condition, one sub-table per chain task so two chain
tasks in one `--runs` dir don't blend their step numbers together).

### Session continuation: how each condition keeps ONE session across steps

Step 1 launches exactly like the single-shot condition already does above,
and its `session_id` is read back from `stdout.json`, same as every other
run. Every later step then has to launch a SEPARATE process (there is no
long-lived agent process to feed a second message to) that resumes that
exact session -- picked, over several rejected alternatives, to be as close
to equivalent between vanilla and zirv as the two CLIs allow:

- **vanilla**: `claude -p --resume <session_id> --output-format json --model
  <model> [--settings ... | --setting-sources ...]`, new step prompt on
  stdin -- claude's own documented resume mechanism, nothing else involved.
- **zirv / zirv-nojev / zirv-proxy / zirv-jev-\***: `zirv ctx exec --agent
  claude -- <claude.exe> -p <prompt> --resume <session_id> --output-format
  json --model <model> --setting-sources project,local` -- i.e. the FULL
  claude invocation handed to `zirv ctx exec` after `--`, exactly as an
  operator would type it by hand, instead of the usual `--prompt <text> --
  ...`-flags-only shape.

That second shape needed a live probe (2026-09-24) to get right, and is
worth recording so nobody "fixes" it back to the obvious-looking form:

1. **Rejected**: `--prompt <text> -- ... --resume <old-id>` (the natural
   extension of the single-shot shape). `zirv ctx exec`'s own `headless_cmd`
   -- used whenever `--prompt` makes zirv build the launch itself --
   ALWAYS mints and injects a FRESH claude `--session-id` ahead of the
   trailing args, unconditionally, not only on a restart. Result: claude
   sees a fresh `--session-id` plus a `--resume` naming a DIFFERENT id, and
   silently starts a brand-new, unrelated conversation -- no error, the
   first turn's `parentUuid` is `null`, and the `session_id` echoed back in
   the JSON result does not match the one that was supposed to be resumed.
2. **Rejected**: also passing zirv's own top-level `--session-id <old-id>`
   so both ids agree. Claude then hard-errors: `Session ID <id> is already
   in use` -- `--session-id` names a FRESH id to mint, never an existing one
   to reopen.
3. **What works**: skip `--prompt` (and zirv's own `--session-id`) entirely
   and hand `zirv ctx exec` the full claude invocation, program name and
   all, after `--`. With a real program name (not a bare flag) leading the
   trailing command, zirv passes it straight through instead of building its
   own `headless_cmd` -- so claude's `--session-id`/`--resume` are never
   double-set. Verified live: the JSON result's `session_id` matches the
   resumed id exactly, `num_turns` reflects the accumulated conversation,
   and zirv's own supervision lines ("sandbox posture", "system prompt
   composed", the safety-hook `--settings <launch-settings>` file) still
   appear on stderr -- supervision stays attached even though zirv is not
   the one building the launch this time.

The harness proxy (`zirv-proxy`/`zirv-jev-*`) intake call
(`zirv ctx proxy --json <prompt>`) runs ONLY before step 1, never again on a
later step. This mirrors `chat.rs::proxy_intake`, which unconditionally
skips the intake view whenever `zirv chat` is resuming an existing
conversation (its own early `if args.simple || args.resume` return) -- a
follow-up message in an already-routed conversation is not re-routed, only
a brand-new one is. Step 1's proxy-decided model and workflow carry forward
unchanged for the rest of the chain. Every `[jev]` gate env var
(`jev_gate_env_for`) is set identically on every step's subprocess, so
zirv's supervision (rot scoring, compaction advisories, hooks) stays
engaged for the whole chain, not just its first message.

### Grading a chain run

Each step is graded immediately after it completes, against the repo state
at that point, using ONLY that step's own hidden tests
(`hidden/step_NN/*.py`, copied into `tests_hidden/` and removed again before
the next prompt is sent -- the agent must never see a hidden test, including
one from a step it already finished). A step with no hidden tests but a
`rubric/step_NN.md` (pure doc/summary steps, e.g. `t23_afternoon`'s final
wrap-up) is graded by the same blind-judge machinery as a top-level
`kind=judge` task instead. The run's overall `score` is the mean of every
graded step's score. Cost, tokens, turns, and wall-clock are summed across
steps into the same top-level `result.json` fields every other task kind
uses (`total_cost_usd`, `wall_s`, `num_turns`, ...) plus a `"steps": [...]`
list with the same fields per step -- so `aggregate.py`/`compare.py` work on
a chain run's numbers unchanged, with no chain-specific code needed there
beyond the per-step table `compare.py` adds when it sees one.

The work-quality judge (`call_quality_judge`, opus) runs once, after the
last step, over the WHOLE session: every step's prompt shown, every step's
final response concatenated, one diff of the repo's final state against the
pristine template -- not once per step. `t23_afternoon`'s own fairness
proof: `tasks/t23_afternoon/reference/step_NN.patch` (one per step, each a
full cumulative diff from the pristine template, `git apply`-able on its
own) scores 1.0 with `visible_ok: true` when applied to a fresh template
copy and graded with that step's hidden tests; a pristine, unpatched copy
scores ~0 on the same tests. Verified for all 8 hidden-test steps (the 9th
is judge-only, so it has no hidden-test score to prove this way) in a
throwaway script outside this directory, never committed.
