# Native multi-agent attention, evidence and rollover UX (N21)

**Date:** 2026-09-13 · **Issue:** #490 · **Roadmap:** #469

## Context

N11 (#480) gave the native runtime a conversation view: a pure reducer from
the journal to a transcript, a composer, and a single-pane dashboard mode
(`zirv chat --runtime native`). Its own design note closed with a list of
what it deliberately did not attempt — a live approval control, mixed
native/wrapped panes, task cards and group ownership, the `@` picker, the
`!` shell. That list is this step's backlog, plus everything the roadmap
issue adds on top: the agent/task overview, evidence panels fed by
authoritative service events, usage/health provenance, visible
compaction/rollover/reconnect, headless parity, an accessibility pass and
bounded virtualization.

The operator's direction for this step was explicit: model the native TUI on
Claude Code's interactive UI rather than inventing chrome — `⏺` bullets with
`⎿` result lines, `>` user lines, a bordered composer with a hint line, a
spinner line with a rotating verb and "esc to interrupt", numbered approval
dialogs, `/` `@` `!` entry modes, `?` for shortcuts, Esc to interrupt and a
double Ctrl+C to quit. The mock
(`docs/design/mocks/2026-09-13-native-pane.html`) was regenerated first and
is the design source for everything below; it draws 80×24, 120×40, 200×50
and a 40-column floor, plus each new surface on its own.

## Decision

### A second module, because it answers to different authorities

`dash::native_pane` reduces ONE session's journal to ONE transcript. Every
surface this step adds is about the work *around* that conversation, and each
is fed by a different durable record: `coordinator::Coordinator` (the task
graph), `delegation::Record`/`Manifest` (receipts and bounded results),
`seat::Seat` (logical identity and generation), `rollover_runtime::Record`
(trigger, every route tried, decision, settlement), `runtime::compaction::
RecoveryHistory` (compactions and resumes), `pool::PoolView` (capacity,
provenance, exclusions). Folding five more record types into `native_pane`
would have cost it the one thing that makes it testable — "journal in,
transcript out". So `dash::native_ux` is a separate module with one rule:

> **Authoritative records in, view model out — never a transcript.**

Every `build_*` function takes already-loaded records and returns plain data.
None reads a JSONL transcript, replays a journal, calls the clock, or touches
the network; `now` is always a parameter. That is what makes 82 of this
step's tests deterministic with no terminal, no runtime and no fixture
directory.

The sharpest case is `build_inspection`: it reads a `delegation::Manifest` —
the bounded result N10 already publishes — and caps its summary a *second*
time at the presentation layer (`INSPECTION_SUMMARY_CAP`). A coordinator
inspecting a worker therefore pays the manifest's bytes, not the worker's
transcript's, however long that worker ran. A follow-up
(`Inspection::follow_up_target`) addresses the *worker*; there is no path in
this module that turns an inspection into input for the pane it was opened
from.

### One classification, used by three surfaces

`AgentState` has nine variants and `classify_agent_state` is the only place a
worker's state is decided, so the overview, the notifications and
`zirv ctx status --agents` cannot disagree. Two decisions inside it matter:

- **`ApprovalNeeded` is separate from `Blocked`.** Both stop a worker, but
  only one is waiting on a *human*, and conflating them is exactly how a
  fleet wedges unnoticed. An outstanding approval outranks the delegation
  record's own phase — a worker can be `Running` from the fleet's point of
  view while it waits on an operator.
- **`DoneUnread` is a receipt fact, not a UI flag.** A completed record whose
  published receipts outnumber its consumed ones is unread; consuming the
  receipt is what downgrades it to `Done`. Nothing is stored in the pane.

Rows are ordered by `AgentState`'s own declaration order and then by short id,
so what needs the operator is always at the top and the order never flickers
between two ticks with identical facts. `Overview::reselect` keeps the cursor
on the same *agent* across a rebuild rather than on the same index — the
overview is rebuilt from records every refresh, and a new row appearing above
the cursor must not silently move the selection onto a different worker.

### Provenance is a type, not a suffix

`Provenance` (`Measured`/`Estimated`/`Unknown`) travels with every value that
has one, and `Measure::text` is the single renderer: a value with unknown
provenance prints `"unknown"` and a measured zero prints `"0 (measured)"`.
The pool view carries capacity but never spend, so the strip states
`pool spend: unknown` explicitly rather than omitting the row — omission is
how a gap becomes a silent `$0.00`. A route that is excluded keeps the pool's
own reason verbatim; an exclusion with no reason is precisely the state an
operator cannot act on. An exclusion naming a harness that is not itself in
the harness list is still rendered, because a route that silently vanished is
worse than one that is visibly refused.

### The rollover guard is a function, not a convention

Criterion 4 asks that input never be submitted to the wrong session across a
rollover. `Continuity` holds what must survive (draft, cursor, queued input,
selection, focus, scrollback, the acknowledged watermark) plus the
`SeatIdentity` the pane believes it answers for. `carry_across` moves it onto
the seat's new identity, preserving everything presentational and
*re-targeting* the queue rather than replaying it into the retired session.
`resolve_submit_target` then compares what the pane believes against the
seat's authoritative identity and returns `Hold { reason }` on any mismatch —
a different seat, a different generation, or a different session. The pane's
`handle_composer_action` runs that check on every send and steer, so a stale
pane queues with a visible notice instead of writing into a retired
generation that may still have a live process behind it.

`carrying_a_pane_across_a_rollover_keeps_the_draft_and_retargets_the_queue`
and `after_a_generation_change_a_queued_draft_targets_only_the_current_
session` pin both halves, including the negative: a pane that has *not* been
carried across is refused outright.

### Approvals: detected from the record, never inferred generously

`StatusFacts.blocked` was hardcoded `false` in N11. It is now a real fact,
read from what the journal actually recorded: `detect_pending_approval`
matches the enforcement broker's own refusal
(`APPROVAL_REQUIRED_MARKER`, a *prefix* match so an ordinary tool result that
quotes the sentence is not an approval) on a tool call, and builds a request
from the tool name and its argument preview. It deliberately does **not**
invent a filesystem scope the record did not carry, and offers no standing
grant at all, because an option whose scope cannot be stated exactly must not
be shown.

The same flag opens the dialog and makes `Enter` queue — one fact, one place.
`dialog_action` claims only digits in range, the arrows, `Enter` and `Esc`;
every other key is `Ignored`, so there is no path from typed text to consent
(`arbitrary_typed_text_can_never_answer_an_approval`). While a dialog is open
`UxState::handle_key` routes *every* key to it before any other region, and
the composer is not drawn at all — leaving it visible would advertise the
wrong control.

`ApprovalRequest::from_enforcement` builds the dialog from the broker's own
`ApprovalRequest` — the one whose `scope_digest` the grant is signed against —
so the dialog can never describe less authority than the grant carries. It is
tested directly but is not reachable from an in-process session yet; see
"What is deferred".

Deferred delivery is the other half of criterion 2: a worker that finishes
while the operator is stuck in a dialog is `defer`red, in order, and released
by `close_approval`. Nothing is dropped and nothing is drawn over the modal.

### Notices are bounded and de-duplicated

`NoticeLog` collapses consecutive identical notices and caps its length. That
is what "stable, low-noise notifications" means in practice: a reconnect that
retries on every 150 ms tick must produce one line, not four hundred. Each
notice renders its glyph *and* its word (`⟳ compacted`, `⤓ rollover`,
`⇄ reconnected`), never colour alone. `notice_from_rollover` renders every
route N19's record says was tried, with its outcome and detail — the part an
operator most needs and the part a "switched model" toast always drops.

### Layout is monotone, and every state carries a glyph

`resolve_layout` is a pure function of width and height. Widening never
removes a panel (`widening_the_terminal_never_removes_a_panel` sweeps 20..240
columns), the main pane is never narrower than 20 columns whatever else is
dropped, and a resize changes how rows wrap but never which rows exist. Every
`AgentState`, `NoticeKind` and `EvidenceKind` has a distinct non-empty glyph
and a distinct label, asserted as a set property rather than case by case, so
"no colour-only state" cannot regress quietly. `SHORTCUTS` is the single table
`?` renders and this note documents: a binding that is not discoverable there
is not a binding.

### Bounds are asserted, not measured

Item 8 asks for a benchmark. A wall-clock assertion on a shared Windows box
with three other workers on it is noise, so the bounds are asserted
structurally instead: `bound_slice` returns a *slice* (bounding a
200,000-item history allocates nothing), `bound_lines` keeps the tail and
prepends one elision marker, `fanout_plan` caps how many sessions a tick
touches, and the pane's own seat reads go through it. The tests drive 200,000
transcript items, 3,000 agents and a 500-session fleet and assert the output
size, not the elapsed time.

### Attaching through the persistent runtime

N20's `dash::link::RuntimeLink` landed while this step was in flight, so a
native pane no longer always opens its own session. `resolve_attach` is the
whole decision and it is pure: a link (which `RuntimeLink::connect` only
returns when the operator's `[session] persistent` gate is on AND something
is actually listening), a runtime that advertised `session.native` in its
`hello`, and a live, reachable **native** seat for this repository. Anything
missing falls back to in-process, which is a working mode rather than a
failure — the same rule `link::ownership` already states for terminals.

`NativePaneRuntime::session` therefore became `Option<InteractiveSession>`.
That is the load-bearing change, not a convenience: opening a second
in-process session for a seat the runtime holds is exactly the
two-supervisors-on-one-conversation failure `link::RUNTIME_OWNS_IT` exists to
prevent, so an attached pane has **no** local session at all, and its
identity (seat short id, journal session, generation) is held directly rather
than read back off a session object that may not exist.

What changes with the transport and what does not:

- **Rendering does not.** The journal is the same durable SQLite file the
  runtime writes, so `build_transcript` and every renderer are untouched.
  Protocol v1's `session.journal` cursor replaces the in-process progress
  channel as the *cue* to re-read, and a page that comes back with `gap: true`
  — the runtime saying the cursor cannot be continued — becomes a visible
  reconnect notice rather than a silent resynchronization.
- **Every action does.** Submit and steer go out as `session.send_input` with
  this pane's own idempotency key, so a reconnect that resends cannot start a
  second turn. Steering in particular no longer writes the journal directly:
  a second writer on a conversation the service owns is precisely what the
  runtime exists to prevent. Interrupt is `session.interrupt` (which ends the
  turn, never the session). Shutdown is `session.detach` — the session, its
  journal and its supervisor are untouched, which is the point of the
  persistent runtime.
- **The approval decision does.** `approval_route(persistent && link.is_some())`
  picks `Protocol`, and the dialog's answer is delivered as `session.approve`
  against the **runtime's own** `request_id`, with a denial's guidance as the
  `note`. The dashboard never mints a grant of its own. A gate that is on
  with no link is still the in-process broker, never a silent no-op.
- **The status line says which.** `native` versus `native · runtime`, so an
  operator can tell at a glance whether closing the window stops the
  conversation or merely detaches from it.

Two honest limitations. `SessionFacts` publishes no route identity, so an
attached pane's model, route and context-left render as the placeholder
rather than a guess. And `serves_native()` needs a live negotiated client,
so the routing test pins the seat half of the rule directly and leaves the
capability half to `link.rs`'s own tests against a real server.

### One dashboard, two pane kinds (item A)

The retrofit N11 and the first N21 round both deferred is done, and the shape
it took is the reason it was affordable. `dash::pane::Pane` did **not** become
a `Vec<PaneKind>` threaded through `dash::mod`: the pane's *process-owning*
half moved into `PtyPane` (master, child, lifecycle guard, writer, reader
channel, turn-signal server) behind a `kind: PaneKind` field, and everything
else a pane carries — title, role, verb, registry guard, budget, delegation,
mail bookkeeping — stayed exactly where it was. So the ~164 call sites in
`dash::mod` that ask a pane for its short id, state, spend or address compile
unchanged, and `Vec<Pane>` is still `Vec<Pane>`. The enum is the minimum that
makes the difference expressible, not a new abstraction layered over the old.

Only four operations genuinely differ, and each branches in exactly one place:

- **Rendering.** `render_native_dashboard` draws the whole native frame inside
  the dashboard's own `main_area`; the chrome around it (header, sidebar,
  rule, footer, overlay) is the dashboard's and is drawn by the same code
  either way. `render_grid` and every existing PTY pane rendering path are
  untouched.
- **Input.** A wrapped pane gets the encoded BYTES through its pty writer; a
  native pane gets the KEY, through `native_pane::handle_native_key` — the one
  function that now owns the native key contract. A wrapped pane never reaches
  it (`Pane::native_mut()` is `None`), which is what "native controls only on
  a native pane" means mechanically rather than by convention.
- **Delivery.** `Pane::inject_visible` is the mail sweep's own call. On a
  native pane it routes to `NativePaneRuntime::deliver`, which goes through
  the composer's **submit path** — so mail is subject to the same
  `resolve_submit_target` rollover/generation guard the operator's own `Enter`
  is, and never types into a pty that does not exist.
- **Lifecycle.** A quit sequence, or `InteractiveSession::shutdown` /
  `session.detach`. `PaneKind::Ended` is what makes the native half idempotent
  without a second flag beside `done`: shutting the session down consumes the
  driver, and the release profile is `panic = "abort"`, so `Drop` cannot be
  relied on.

`zirv chat --runtime native` is now the dashboard's FIRST PANE rather than a
loop of its own, and the 171-line single-pane loop is deleted: one event loop,
one raw-mode/alternate-screen sequence, one key contract. A dashboard spawn
request naming the native runtime opens a native worker pane after the checks
that already ran (argv guard, repo gate, workdir roots, pane cap, delegation
depth cap, agent allowlist) — and is refused, rather than accepted and
silently unaccounted, when it asks for a work group or a token/time ceiling,
because those are accounted from a harness transcript and a per-provider
reservation a native session does not have. The restore roster records each
pane's kind and a native entry comes back through `open_native_pane`, so
`resolve_attach` decides all over again whether the persistent runtime already
holds the seat — the one decision that must not be skipped, for exactly the
reason `link::RUNTIME_OWNS_IT` exists.

Not touched, deliberately: raw-mode handling, `wrap.rs`, any `#[cfg(unix)]`
code, and the existing PTY pane's own rendering.

### Approvals are real now (item B)

`ApprovalMode::Interactive` existed in N04's broker but nothing could reach
it: `runtime::native::session_broker` built every native session `Headless`,
so the dialog could only deny. Three things changed, and the smallest of them
is the load-bearing one.

`enforcement::InteractiveApprovals` is a channel the pane drains plus a
session-scoped set of remembered scopes. When an action needs approval and
carries no grant, the broker raises a typed `ApprovalPrompt` on it and
**blocks that tool call** until a decision arrives. `ApprovalPrompt::decide`
takes `self` by value and the reply channel holds exactly one message, so a
decision is applied at most once *by construction* — there is no second send
to race with.

The mode is **derived from the gate** rather than passed beside it:
`session_broker` takes `Option<Arc<InteractiveApprovals>>` and is interactive
exactly when there is a live channel to ask on. That makes the invariant
structural rather than conventional: there is no way to build a broker that
says it will ask with nobody listening, and no way to build one with a dialog
it never consults. Every headless caller passes `None` and gets precisely the
pre-#490 construction, so "headless cannot be approved away" stays true no
matter who calls what.

`Remember` is deliberately the narrowest thing that is still useful: it
suppresses the next request whose `scope_digest` is byte-identical — the same
tool, the same resolved paths, the same policy and claims fingerprints — for
the rest of THIS session, and nothing else. It is never persisted and never
widened to a directory. That is also why the dialog may offer it at all: the
rule "an option whose scope cannot be stated exactly is never shown" is
satisfied by the digest, where a transcript-derived request (which carries no
digest) still gets no standing grant at all.

An interrupt cancels every blocked call: each returns `Cancelled`, the call
fails closed with `ApprovalRequired`, and a decision that arrives afterwards
finds the receiver gone and reports `false` — nothing is released twice.
`InteractiveSession::interrupt` cancels the gate as well as the turn, and
`shutdown` closes the channel before joining the worker, so an operator
walking away cannot park a thread on an answer no dialog will ever draw.

The protocol path (`session.approve`) is unchanged; `approval_route` still
picks it for a runtime-owned conversation, and the dashboard still never mints
a grant of its own there.

### The mock is the acceptance target

Operator direction (2026-09-14): where the renderer deviates from
`docs/design/mocks/2026-09-13-native-pane.html`, the renderer changes. Two
deviations were closed in this round, both in the pane's own interior — the
chrome around it is the ordinary dashboard's now (item A), so the mock's
header chip, sidebar sections and footer key line are drawn by `dash::ui`,
unchanged:

- The **activity line** now reads `✻ <verb>… (esc to interrupt · 1m 12s ·
  ↓ 3.4k tokens)` — interrupt hint first, a minute/hour-aware elapsed, and a
  `k`-scaled token count that truncates rather than rounds up (a total that
  reads higher than it is, is the one direction an operator cannot check).
- The **composer hint line** is the mock's three columns: `? for shortcuts`
  hard left, the composer mode and the key that cycles it centred, `⧗ N
  queued` hard right and absent entirely when nothing is queued. At the narrow
  floor each column drops to its shortest honest spelling instead of
  overflowing.

Four snapshot-style tests pin that skeleton at 40, 80, 120 and 200 columns
from fixed fixture facts: the box's full-width rows and rounded corners, the
hint line's three columns and their bounds, the activity line's exact reading,
and which panels each width resolves.

Known remaining deviations, all wording rather than layout, and none of them a
colour-only state: the mode label keeps this repo's own vocabulary
(`accept-edits mode`) rather than the mock's prose (`accept edits on`); the
spinner cycles the braille frames the pane already used rather than the mock's
single `✻`; and the sidebar/overview section headers keep their existing
`dash::ui` spelling.

## What is verified

82 deterministic tests across `dash::native_ux` (66) and the new
`dash::native_pane` surfaces (16), none needing a terminal, a live runtime, a
network call or a clock (PR #544's review pass, below, adds a further two
that deliberately DO use a real loopback transport, because that is exactly
what they are pinning):

- Overview: approval outranks phase; unread/consumed receipts; urgency
  ordering; an undelegated task node as a queued row; a parked seat as
  draining; a missing model as an explicit unknown; selection following the
  agent across a rebuild; click-to-row mapping; distinct glyphs per state.
- Inspection: only the bounded manifest is read; an oversized summary is
  capped and says so; evidence classification; the rendered line cap.
- Provenance: exclusions keep their reason; measured vs unknown signals; an
  unknown measure never contains a zero; a measured zero stays a zero; an
  empty billing class is the placeholder; a degraded snapshot says so.
- Continuity: the full carry-across; the generation guard in both directions;
  a different seat refused with a reason; the no-op case.
- Approvals: three numbered options with the exact scope; no "don't ask
  again" without a directory; number keys and arrows; arbitrary text refused;
  the protocol/broker routing; deferred mail held and released in order and
  de-duplicated; an answered approval never reopening.
- Driver: the modal claiming every key; focus routing and the composer
  keeping its printable characters; overview navigation and inspect; Esc
  closing an inspection before interrupting; the follow-up target; a refresh
  keeping the cursor; the panel staying inside its line budget with 3,000
  agents.
- Presentation: the bordered composer's exact box width at 60 and its
  survival at 40; the hint line naming what Enter does in all three states;
  `/` and `!` completion rows; `@` offering nothing without a workdir; the
  spinner only while a turn is in flight and its deterministic verb rotation.
- Layout/accessibility: the four terminal sizes; monotone widening; resize
  changing wrapping not rows; a CJK path measured by display width.
- Bounds: 200,000 items; line bounding with an elision marker; a 500-session
  fanout; 3,000 agents inside the row and line budgets.
- Attachment routing: `a_pane_attaches_in_process_unless_the_runtime_owns_a_
  live_native_seat` (no link, a wrapped seat, an unreachable seat and no seat
  at all all fall back in-process) and
  `an_approval_on_a_runtime_owned_session_routes_over_the_protocol`.

## What is deferred

- ~~**Granting an approval from the pane.**~~ **Done** — see "Approvals are
  real now (item B)" above. PR #544's review pass removed
  `ApprovalRequest::from_enforcement` from `dash::native_ux` as dead code
  while this was still deferred, and warned that whichever wiring landed
  first would need a constructor shaped by the channel it was actually for.
  It did: the conversion is `native_pane::dialog_request_from_broker`,
  written against the `enforcement::ApprovalPrompt` the pane now drains, and
  it lives in that module rather than back in the view model.
- ~~**Mixed native + wrapped panes in one dashboard.**~~ **Done** — see
  "One dashboard, two pane kinds (item A)" above.
- ~~**The `RuntimeLink` / persistent-runtime client path.**~~ **Done** after
  the rebase onto `release/native-harness` brought N20's `dash/link.rs` in —
  see "Attaching through the persistent runtime" below.
- **Per-item transcript selection and copy.** `set_selection`/
  `clear_selection` and the continuity record carry a selection, but no key
  creates one and there is nothing to copy into.
- **Attention/mail sweep into a native pane.** Worker completions are
  surfaced from the delegation records themselves; `mail::list` is keyed by
  the repository slug and reaching it from here would add a `repo_slug(`
  consumer to a dashboard module. `zirv ctx status`'s own mail section
  remains the complete view.
- **Wall-clock performance numbers.** Bounds are asserted structurally, as
  above. The cross-platform UX evidence is the deterministic view-model tests
  plus the existing CI matrix; no macOS or Linux terminal was driven by hand
  for this step, and no `#[cfg(unix)]` code was added or changed.
